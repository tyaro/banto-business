# ADR-0006: 知識ドキュメントは in-repo に集約し、GitHub Projects は揮発的ステータス専用に限定する

## コンテキスト

テンプレートが M10〜M24 まで積み上がり資産が増えたことを受け、GitHub の
**Projects（作業ボード）／ Wiki** を活用すべきかを検討した。現状の運用は:

- ドキュメントは in-repo に**一本化**している（CLAUDE.md 冒頭「ドリフトを
  避けるため一本化」、AGENTS.md が唯一の道案内）。「なぜ」は3分類
  （コードコメント / conventions.md / ADR）で**同じ理由を2箇所に書かない**。
- **コードが docs を大量に参照する。** `spec §N` / `spec M14` /
  `docs/*-plan.md §` 形式の参照が **794 箇所・205 ファイル**（2026-07-30 計測、
  `rg 'spec (§|M)\d|docs/[a-z-]+\.md'`）。conventions §12 の「モジュール冒頭で
  仕様節を引く」文化そのもの。参照は行番号でなく**ファイル + シンボル名 +
  仕様節**で張る（conventions 冒頭）。
- conventions.md の一部は `verify:architecture`（CI）が**機械検査**し、正当な
  例外はコード内コメント + スクリプト許可リストの**ペア**で管理する。
- planning は roadmap.md / template-scope.md / `*-plan.md` に、決定は ADR に
  ある。issue/PR は**滞留させず**マイルストーン単位の PR でマージ・クローズ
  する運用（2026-07-30 時点で open issue/PR = 0）。

問われたのは2つ: (1) AI から見て「docs 一本」と「Projects 活用」のどちらが
良いか、(2) 人と AI の協調作業ではどうか。さらに「README 以外を Projects に
一本化」という案も俎上に載った。判断が必要なのは **Banto の知識をどの媒体に
置くか**であり、これは横断的な運用規約になるため ADR に残す。

## 決定

**知識（不変条件・仕様・スコープ判断・設計判断・実装計画・レシピ）は
引き続き in-repo の `docs/` に集約する。GitHub Wiki は採用しない。**

**GitHub Projects は、採用するとしても「揮発的な実行ステータス／調整」専用の
レイヤに限定する** — roadmap のマイルストーン状態追跡・今後のタスク管理など。
**知識を Projects へ移さない。** 線引きは「README vs docs」ではなく、docs の
中を貫く **「不変の知識（in-repo）／ 可変のステータス（Projects 可）」** に置く。

導入トリガ（Projects をステータス層として起こす条件）は、v2 バックログ
（roadmap §3）が**並行実行フェーズに入る**か、**外部採用者から issue が
立ち始める**か、banto-industrial と連動した横断作業が発生したとき。それまでは
docs 一本で足りる。

## 検討した代替案

- **案A（採用）: 知識は in-repo docs、Projects はステータス専用の任意レイヤ。**
  利点: 794 参照・機械検査・PR 原子性（ルール変更をコードと同じ diff で
  レビュー）・バージョン結合（あるコミットの docs はそのコミットの不変条件）を
  すべて保つ。AI はリポジトリ内の docs を **API ゼロ・コミット整合**で常に
  読める。ステータスという docs が苦手な領域だけを、構造化フィールドを持つ
  ボードに逃がせる。欠点: 知識とステータスで媒体が2つになる — ただし役割が
  分離しており同じ事実を二重に持たないため、ドリフトは原理的に起きない。
- **案B（不採用）: Wiki に docs を出す。** Wiki は**別の git リポジトリ**で
  コードと一緒にバージョン管理されず、PR レビューを通らず、コード近接でない。
  `spec §N` の 794 参照が grep 不能・コミット非固定の外部リンクに化け、
  conventions §12 と「コードを一次情報とする」運用が崩れる。既存の `docs/` は
  バージョン管理・PR レビュー・コード近接・相互参照を備えた **Wiki の上位互換**
  であり、Wiki を足す利得が無い。
- **案C（不採用）: README 以外を Projects に一本化。** 案B の欠点をすべて
  満たした上でさらに悪い。Projects は draft issue でテキストを持てるが、
  相互リンクが弱く、ADR の「番号付き・不変・追記のみ」という文書ジャンルを
  表現できない。794 参照・バージョン結合・PR 原子性を壊し、AI は不変条件を
  読むたび（落ち得る）API を叩く羽目になる。しかも Projects の強みである
  **フィルタ可能な構造化フィールド（status/priority/assignee）**は時間不変の
  知識には無意味で、ボードを**ただのテキスト置き場**として使い弱点だけ継承
  することになる。ステータス表（roadmap のマイルストーン状態）が Projects
  向きなのは正しいが、それは docs 全体ではなく docs 内の**ステータス部分に
  限った**話。

## 帰結

- **conventions §12 の参照文化と機械検査を維持する義務。** コードは引き続き
  `spec §` / `docs/*-plan.md §` を in-repo docs へ張る。知識ドキュメントを
  リポジトリ外へ出さない。
- **Projects を採用する場合のレーン規律**: ボードは「ステータス + そのタスク
  限定の議論」まで。**1タスクを超えて一般化する理由は、issue に留めず PR で
  ADR / conventions に昇格させる。** 永続的な知識が issue/ボードだけに存在する
  状態を作らない（案B/Cを退けた理由をボード運用の中でも守る）。
- **AI 消費**: 知識は in-repo なので **API ゼロ・コミット整合**で常に手元にある
  （不変条件を読むのに外部サービスの可用性へ依存しない）。ステータスは本質的に
  ライブなので API 越しでも問題ない — 役割に媒体が合っている。
- **人と AI の協調**: Projects を起こしたときは、それが**人と AI の共有調整面**
  （状態・担当・受け渡し）になる。一方 docs は**両者が読む唯一の真実源**の
  ままにする。委譲モデル（roadmap §7 の 司令塔 → タスク分割 → 委譲）は issue に
  自然に乗る。
- **再検討条件**: 上記「導入トリガ」を満たしたら、Projects をステータス層
  として起こすことを本 ADR は妨げない（それは本 ADR の想定内であり覆しでは
  ない）。逆に、知識を Projects/Wiki へ移す判断をするなら、本 ADR を
  supersede する新 ADR を書く。
