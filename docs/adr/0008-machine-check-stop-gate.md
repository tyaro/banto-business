# ADR-0008: 機械検査を足すかは「3条件ゲート」で判断し、無限追加を止める

## コンテキスト

Banto は「散文の規約を、失敗する CI 検査に変換する」文化を持つ
（`verify-architecture.mjs` の rule 1〜12）。一方でこの文化には自然な増殖圧力が
ある — レビューのたびに「これも機械検査できるのでは」という候補が出続ける。

機械検査には**実装コストだけでなく継続コスト**がある: 誤検知しうる / 将来の
リファクタを縛る / 保守が要る / 新しい担当（人でも AI でも）が理解する必要が
ある。検査を増やしすぎると、**ガードレール自体が保守負担になり、緑を通ったことが
「網羅されている」という偽の安心感を生む**側に傾く。

maintainability-review-2026-07 §4.1 はこの緊張に対し「機械検査はここで打ち止め」と
判断し、その根拠として3つの条件を口伝で持っていた。しかし 2026-08 の保守レビュー
Phase 4 で**新規検査9案**が出て、無条件に足すとこの打ち止め方針と正面衝突する
状況になった。判断基準が口伝のままだと、次のエージェント/レビューが同じ議論を
やり直すか、基準なく足してしまう。**判断基準を破れない ADR に昇格させる必要がある。**

## 決定

**新しい機械検査を足すかは、次の3条件を _すべて同時に_ 満たすかで判断する
（3条件ゲート）。1つでも欠ければ機械化しない。**

1. **背骨である** — 壊れると重大（不変条件の中核。ビルド/実行/認可・セキュリティの
   いずれかが崩れる）。
2. **静かに壊れる** — レビューやビルドで気づけない（← 最重要の条件。可視な差分で
   壊れるものは機械化の価値が低い）。
3. **AI が無自覚に壊しうる** — エージェントがうっかり踏みやすい。

加えて、**誤検知が出やすい（正当/不当の線引きを grep が判断できない）検査は
採用しない** — 大きな許可リストが必要になる検査は形骸化し、条件を満たしても却下する。

この ADR は判断基準であると同時に、**候補の採否台帳**でもある（下の「9案の選別」）。
今後の新規候補も、採否とその理由を1件ずつここに追記する（バックフィルはしない）。
検査の実体は `scripts/verify-architecture.mjs`、規約本文は `conventions.md` の該当節に
置き、本 ADR には複製しない。

## 検討した代替案

- **案A（採用）— 3条件ゲート。** 「背骨 + 静かに壊れる + AI が壊しうる」を全て
  満たすものだけ機械化する。利点: 継続コストに見合う検査だけが残り、緑の意味が
  保たれる。欠点: 一部の「あれば良い」検査（見出しパリティ等）を意図的に見送るため、
  網羅感は下がる（が、それは偽の網羅感を避けるための意図的な選択）。
- **案B（不採用）— 機械化できるものは全部足す。** 却下理由: 継続コスト（誤検知・
  リファクタ拘束・保守・認知負荷）が線形に増える。かつ**浅いプロキシ検査**（見出し数
  一致など、中身のズレを見ないもの）は緑でも実質を保証せず、**偽の安心感**という
  本文化が名指しで戒めるアンチゴールそのものになる。
- **案C（不採用）— 機械検査はもう一切足さない。** 却下理由: 今回の9案には、
  **本当に静かに壊れる背骨**が2つ含まれていた（マイグレーション方言の欠落は PG が
  smoke CI のみのため気づけない / CSP 2定義のドリフトは cross-check テストが無く
  src-tauri も非コンパイルのため気づけない）。一律凍結はこの2つの実損を見逃す。
  打ち止めは「基準で選別する」であって「思考停止で止める」ではない。

## 帰結

- **今後の新規検査候補は、実装前に3条件ゲートを明示的に当て、採否と理由を本 ADR の
  表に1行追記する**（バックフィルはしない = 次に触れるとき1件ずつ）。
- **「見送り（defer）」を覆すのは、実際の _定常的な_ ドリフトが観測されたときに限る**
  — 一度きりの一括改名イベント（案3の63件のような）は覆す根拠にしない。
- 採用した検査には、意図的例外を**理由付きの許可リスト**で管理する余地を持たせる
  （既存 rule と同じ流儀）。rule 11/12 は現状その必要が無いほど誤検知面が狭い。
- 機械検査の網羅性を「緑 = 全部守られている」と読まない。本 ADR の表が
  「何を機械が見て、何をレビュー/テストが見るか」の一次情報になる。
- rule 11/12 の実装上の限界を明記する義務: rule 11 はファイル名/連番の対称のみ
  （同名ペア内の型差は §11 の意図的分岐でレビュー担保）。rule 12 は Rust const 文字列の
  抽出に依存する（const を単一行・raw string・`concat!` へ整形すると抽出が壊れる →
  その時は「検査を更新」で fail するので静かには壊れない）。
