# デバイス間同期（Phase 8）

PC と Android 端末（Pixel）で同じ業務データを扱うための同期方式。

**前提（2026-08-20 決定）**

- **スマホが操作の主体。** 工数・経費・出張の入力は外出先で行い、PC は大画面での
  整理と、請求・入金・採算のためのデスク作業に使う
- **外出先ではオフライン。** LAN にも VPN にも繋がらない前提で、端末単独で
  読み書きが完結する
- **同期は自宅 LAN に戻ったときだけ。** インターネットに何も公開しない。
  クラウドも VPN も使わない

```
外出先        Pixel（ローカル SQLite・完全オフライン）
   │
   │ 帰宅して LAN に乗る
   ▼
自宅 LAN      Pixel  ⇄  banto-serve（PC）
                        既存の REST（Bearer + X-Banto-Client）の上に
                        同期用の入口を足す
```

---

## 1. 同期する範囲

**全テーブルを双方向にはしない。** 双方向は衝突解決を伴うので、本当に両方で
編集するものだけに絞る。

| テーブル                                                   | 方向                     | 理由                                                                                                           |
| ---------------------------------------------------------- | ------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `customers` / `projects`                                   | **双方向**               | 現場で新しい案件が立つ。スマホが主体である以上、マスタもスマホで作れないと使えない                             |
| `work_categories` / `expense_categories` / `cost_rates`    | **双方向**               | 同上。ただし変更頻度は低い                                                                                     |
| `work_logs` / `expenses` / `trips`                         | **双方向**               | Phase 8 の主目的                                                                                               |
| `invoices` / `invoice_lines` / `invoice_tax_summaries`     | **同期しない**           | 請求は PC 専用（下記 2 節）。スマホは請求画面を持たない                                                        |
| `payments` / `payment_allocations`                         | **同期しない**           | 同上                                                                                                           |
| `settings`（事業者情報・端数処理）                         | **PC → スマホ の一方向** | 請求のための設定。スマホで編集する理由が無い                                                                   |
| `attachments`（領収書）                                    | **スマホ → PC の一方向** | 撮るのはスマホ。正本は会計ソフト側なので（`CLAUDE.md` 1.6）取りこぼしても致命的でない。DB とは別チャネルで送る |
| `audit_log` / `users` / `user_roles` / UI 設定 / `backups` | **同期しない**           | 端末ごとのもの                                                                                                 |

### 1.1 双方向の対象は8テーブル

`customers` `projects` `work_categories` `expense_categories` `cost_rates`
`work_logs` `expenses` `trips`。

このうち **`work_logs` / `expenses` は `invoiced` フラグを持つ**。これは PC が
請求書を確定したときに立てるもので、スマホには**結果として降りてくる**
（PC が更新した行が同期で届く）。請求そのものは同期しないが、請求の**影響**は
届く、という非対称がある。

## 2. 請求・入金を PC 専用にする理由

**請求書番号（`INV-YYYY-NNNN`）は「その年の最大番号 + 1」で採番している**
（`invoices.rs::next_invoice_number`）。オフラインの 2 台がそれぞれ確定すると
同じ番号の別の請求書ができ、取引先に PDF を渡した後では取り返しがつかない。

請求を PC 専用にすると、確定する端末が常に 1 台なので**この問題が原理的に
起きない**。案件番号（`YYYY-NNN`、F-M3）も同じ構造だが、こちらは内部番号で
手修正できるため（F-M3）、実害は小さい。それでもスマホ側の採番は
デバイスレンジ（3 節）で分離する。

## 3. id の採番 — デバイス別レンジ

### 3.0 対象は 5 テーブル（8 テーブルではない）

双方向対象 8 テーブルのうち、**id 衝突が起きるのは 5 つだけ**。

| 主キー                                     | テーブル                                              | 衝突するか                                |
| ------------------------------------------ | ----------------------------------------------------- | ----------------------------------------- |
| `INTEGER PRIMARY KEY AUTOINCREMENT`        | `customers` `projects` `trips` `work_logs` `expenses` | **する。** 2 台が独立に採番するため       |
| `TEXT PRIMARY KEY`（利用者が決めるコード） | `work_categories` `expense_categories` `cost_rates`   | **しない。** 同じコードは同じ行を意味する |

後者で両端末が同じコードを作った場合は、id 衝突ではなく**内容の衝突**
（6 節）として扱う。「同じものに 2 つの定義がある」のであって、
「別のものが同じ番号を持った」のではない。

### 3.1 5 テーブルの採番

PostgreSQL 側は `BIGINT GENERATED BY DEFAULT AS IDENTITY`。

**採用：デバイス別の id レンジ。**

| 端末                | レンジ                         |
| ------------------- | ------------------------------ |
| PC（デバイス 0）    | 1 〜 999,999,999               |
| Pixel（デバイス 1） | 1,000,000,000 〜 1,999,999,999 |
| 以降                | 10 億刻みで割り当てる          |

- レンジが重ならないので、**id が全端末で同じ行を指す**。外部キーの値も
  そのまま通り、同期の際に id を translate する必要が無い
- **既存データの振り直しが不要。** PC は今の 1〜 のまま使い続け、新しい端末に
  高いレンジを割り当てるだけで済む。Phase 7 で実データを入れた後でも手戻りが
  出ない

### 3.2 ULID / UUID を採らない理由

id を文字列にすると同期は素直になるが、全テーブル・全外部キー・各サービスの
`ColumnMap`・`DataProvider` の `id` 型に波及する。

### 3.3 「INTEGER PK 据え置き + `uid TEXT UNIQUE` を別に持つ」を採らない理由

同期のたびに uid ↔ ローカル id を変換することになり、**変換を1箇所でも間違えると
「工数が別の案件に付く」という金額バグ**になる。`CLAUDE.md` 第1章の趣旨に
照らして避ける。

### 3.4 デバイス番号の持ち方

`settings` に `device.id`（整数）を持ち、初回起動時に決める。レンジの起点は
`device.id * 1_000_000_000 + 1`。SQLite の `AUTOINCREMENT` は
`sqlite_sequence` の値から続きを採番するので、初期化時にレンジ起点 − 1 を
書き込む。

**バックアップの復元をまたいだ端末間コピーはしない。** 既存の Backup
（`VACUUM INTO` による DB 全体のスナップショット + 起動時ファイル差し替え）は
**置換であって同期ではない**。片方の DB をもう片方へ復元すると、その間に
入れた行が消える。同期の土台には使わない。

## 4. 変更の追跡 — outbox

「前回同期以降に変わった行」を知る必要がある。

`updated_at` は全テーブルにあるが、業務テーブルの中身は各サービスの
`today_expr`（`date('now')` / `CURRENT_DATE::text`）で、**日付までしか入って
いない**。同じ日の更新は全て同じ値になるので、watermark には使えない。
端末間の時計ずれの影響も受ける。

（`banto_storage::Dialect::now_expr` は `datetime('now')` / `NOW()` を返すが、
業務テーブルはこれを使っていない。SQLite に日時型が無く全ての日時が TEXT
なので、PostgreSQL 側は `::text` へ明示的に落とす必要があり、各サービスが
自前の `today_expr` を持っている。）

**採用：変更ログ（outbox）テーブルを別に持つ。**

```
sync_outbox
  seq          INTEGER PRIMARY KEY AUTOINCREMENT   -- 端末内で単調増加
  table_name   TEXT NOT NULL
  row_key      TEXT NOT NULL      -- 整数 PK は10進文字列、コード PK はコードそのもの
  op           TEXT NOT NULL      -- INSERT / UPDATE / DELETE
  changed_at   TEXT NOT NULL
```

`row_key` を `INTEGER` ではなく `TEXT` にしているのは、双方向対象に
`TEXT PRIMARY KEY` のマスタが 3 つあるため（3.0）。両方を 1 つの表で
扱えるようにする。

- 同期は「相手が持っている最後の `seq` より後」を送るだけ。時計に依存しない
- 取りこぼしが構造的に起きない

`sync_state` に、相手端末ごとの「どこまで送ったか / どこまで受けたか」を持つ。

### 4.1 記録は DB トリガで行う（当初案からの変更）

当初は「書き込み系のサービスが、行の変更と**同じトランザクション内で** 1 行
足す」と書いていた。実装に入って **書き込みの入口が 19 箇所**あると分かったので、
DB トリガ（`migrations-*/0024_sync_outbox_triggers.sql`）に変えた。

| 入口                                                                               | 数         |
| ---------------------------------------------------------------------------------- | ---------- |
| 各サービスの `create` / `update` / `delete`                                        | 15         |
| `invoices.rs` の確定・取消（`work_logs` / `expenses` の `invoiced` を直接 UPDATE） | 4          |
| `trips.rs` の一括生成（`work_logs` / `expenses` を直接 INSERT）                    | 上記に含む |

手で足す方式だと、**1 箇所忘れただけでその変更は永久に同期されない**。しかも
忘れたことは「相手に届かない」という形でしか現れないので、気付くのが遅れる。
新しい書き込み経路を足したときも同じ穴が空く。

トリガなら、行の変更と同一トランザクション（トリガは呼び出し元の文の一部）で、
どの経路から書いても記録され、経路が増えても追従がいらない。

代償は「ロジックが DB 側にある」こと。方言ごとに 2 セット書く必要があり、
§11 の 2 方言対応と同じ保守コストがかかる。それでも **「取りこぼしが構造的に
起きない」という outbox 採用の理由そのもの**を守れるほうを採った。

`op` は物理削除をしないので INSERT / UPDATE の 2 トリガで足りる。論理削除は
UPDATE なので、`deleted_at` が NULL から非 NULL へ変わった UPDATE を `DELETE`
として記録する。

マイグレーションのシード（作業分類・経費分類の初期行）はトリガ作成より前に
流れるので記録されない。**両端末が同じマイグレーションを流すので初期行は最初から
双方に同じものが在り**、同期する必要が無い。

## 5. 削除 — 論理削除（トゥームストーン）

行が消えているとき、「削除された」のか「まだ届いていない」のかは区別できない。

**採用：`deleted_at TEXT`（NULL なら生存）を双方向対象の 8 テーブルに足す。**

- 物理削除をやめ、`deleted_at` を立てる。値は**日付ではなく日時**
  （`crate::sync::deleted_at_expr`）。同じ日に消して作り直した行を区別できないと
  困るため、業務日付とは粒度を変えている
- **既存の全参照に `WHERE deleted_at IS NULL` が要る。** 一覧・詳細・採算集計・
  請求候補・カレンダー集計と参照箇所は広い。Phase 8 で最も手数のかかる部分
- トゥームストーンは消さない（消すと再出現する）。件数は個人事業の規模なら
  問題にならない

### 5.1 墓石はコードを保持し続ける

`customers.code` / `projects.code` は `UNIQUE`。**墓石も列を持ったまま残るので、
削除した顧客・案件のコードは再利用できない。** 削除済みの `C001` と同じコードで
新規作成すると、利用者からは見えない行との重複としてエラーになる。

コードは識別子であり、消した相手のコードを別の相手へ付け替えると過去の記録が
読めなくなるので、再利用できないこと自体は正しい。ただし**エラー文言だけ見ると
理由が分からない**ので、実運用で問題になるようなら「削除済みに同じコードがある」
と伝える形にする（Phase 7 の評価で判断する）。

### 5.2 親を消すときは生きている子だけ数える

墓石を数えると、実際には何も残っていないのに「案件が2件あるため削除できません」
と出て、**永久に消せない親**ができる。

物理削除の頃は外部キーが弾いていた経路も、論理削除では行が消えないので外部キーが
何も言わない。放置すると、子がぶら下がったまま親だけ見えなくなる。そのため
`projects` には新しくガードを置いた（`work_logs` / `expenses` / `trips` /
`invoice_lines`）。`customers` の既存ガードにも請求書・入金を足した。

| 親          | 数える子                           | 墓石を除くか                         |
| ----------- | ---------------------------------- | ------------------------------------ |
| `customers` | `projects`                         | 除く                                 |
| `customers` | `invoices` / `payments`            | 除かない（同期しないので墓石が無い） |
| `projects`  | `work_logs` / `expenses` / `trips` | 除く                                 |
| `projects`  | `invoice_lines`                    | 除かない（同上）                     |

## 6. 衝突

同じ行を両方の端末で編集した場合。

**採用：自動で片方を捨てない。同期時に提示して選ばせる。**

一人利用なので衝突は稀で、稀だからこそ「気づかないうちに入力が消えた」が
起きると数字を信用できなくなる。last-write-wins は端末間の時計ずれに依存する
うえ、捨てた側が記録に残らない。

### 6.1 請求済みの行は凍結されている（決定 C-20）

`invoiced = 1` の工数・経費は**両端末とも編集・削除できない**
（`WorkLogsService` / `ExpensesService` の `ensure_not_invoiced`）。これにより
衝突の対象が「未請求の行」に限られ、範囲がさらに狭まる。

ただし**同期の遅れによる1つの経路は残る**。

```
スマホ: 行 X を編集（オフライン）
PC    : 同期前の古い X を含めて請求書を確定 → X.invoiced = 1
        ↓ 帰宅して同期
        PC は「請求済みになった」、スマホは「金額を直した」
```

この場合、**請求書は既に確定済みで取引先へ渡っている可能性がある**ため、
自動で解決しない。提示して、必要なら請求書を取消（赤伝）→ 直す → 再発行、
という F-I8 の手順へ進んでもらう。

「片方が `invoiced` を立てただけ」の自動解決（下表）は、**もう片方が
その行を触っていない場合に限る**。

### 6.2 自動で解決してよい組み合わせ

例外として、**自動で解決してよい組み合わせ**が 2 つある。

| 組み合わせ                                                              | 規則        | 理由                                 |
| ----------------------------------------------------------------------- | ----------- | ------------------------------------ |
| 片方が `invoiced` を 0 → 1 にしただけ（もう片方はその行を触っていない） | PC 側を採る | 請求済みの事実は PC でしか起こらない |
| 両方の全列が同値                                                        | 何もしない  | 衝突ではない                         |

衝突の判定は「双方の outbox に同じ `(table_name, row_key)` があり、かつ前回同期
以降に両方で変更されている」。

## 7. スナップショット原則が効くところ

`CLAUDE.md` 1.2 の設計が、同期に対してそのまま防御として働く。

- **`work_logs.applied_rate` は記録時点で焼き付けてある。** 後からレートマスタが
  同期で届いても、過去の工数原価は書き換わらない。同期で最も怖い
  「後から来たマスタが過去を壊す」が構造的に起きない
- **確定済 Invoice は確定時点の値を持つ。** そもそも同期対象外だが、仮に元の
  `work_logs` が同期で変わっても請求額は動かない

## 8. Android 側の構成

- **Tauri v2**（`src-tauri` は既に v2）。`conventions §2` によりサービス層が
  `tauri` / `axum` に依存していないので、**税計算・採算計算・消込ロジックの
  Rust コードがそのまま乗る**
- PWA + IndexedDB を採らないのは、金額ロジックを TypeScript で二重実装する
  ことになり、`CLAUDE.md` 第6章の「金額が絡むロジックは必ずテストする」を
  2 箇所で担保する羽目になるため
- `keyring`（自動ログイン）はデスクトップ専用なので Android ビルドから外す。
  `window-vibrancy` は既に Windows 限定。**対応済**（手順と検証範囲は
  `docs/android-build.md`）
- **起動時に採番レンジを当てる。** `sync.device.id` を設定しただけでは
  採番は変わらない（3.4）。忘れた端末は既定レンジで採番を始め、同期して
  初めて衝突に気付く。設定が読めないときは起動を止める
- 配布はストアを経由せず、自分の端末へ APK を直接入れる
- **Android ビルドは CI で回す（2026-08-21 に方針変更）。** 当初は「SDK /
  NDK / JDK が要り重い」として足さない判断だったが、**前提の方が間違って
  いた** —— GitHub ホストの ubuntu ランナーにはこの3つが最初から入って
  おり、用意するのは Rust の Android ターゲットだけ。ただし Rust の
  cross-compile と Gradle でビルド時間は伸びるので、**毎 PR では回さず**
  手動起動と月次に限る（`.github/workflows/android-build.yml`）。出るのは
  デバッグ署名の APK で、secrets を使わない

### 8.1 折りたたみ端末の画面

開いた内側はタブレット寸法なので、既存のレスポンシブ（ビジュアル回帰で
768x1024 / 1024x768 を撮っている）がほぼそのまま効く。畳んだ外側は細く、
一覧グリッドを縮めても使えないので、「今日の工数を 1 件足す」だけの
専用画面を別に用意する。

## 9. 新規依存は足さない

同期プロトコルは HTTP + JSON で、REST の土台は既にある。TLS は LAN 内なので
`ADR-0003`（TLS はリバースプロキシ終端）の判断をそのまま踏襲し、rustls を
足さない。`ADR-0002`（最小依存）に抵触しない。

## 10. 実装の順序

1. **スキーマ**：デバイスレンジ / `sync_outbox` / `sync_state` / `deleted_at`
2. **サービス層**：物理削除を論理削除に置き換え、全参照へ `deleted_at IS NULL`、
   書き込み時に outbox へ記録
3. **同期プロトコル**：PC 側（`banto-serve`）に同期の入口を作る。ここまでは
   Android 無しでテストできる（11 節）
   - 3a. 読み取り（handshake / pull）—— PC を書き換えない
   - 3b. 取り込み（push）と衝突の提示 —— PC を書き換える
4. **Android ビルド**
5. **折りたたみ向け UI**

1〜3 は PC だけで作ってテストできるので、Android が動く前に同期ロジックを
固められる。3 を 3a / 3b に割るのは、**PC の DB を書き換える回を独立させる**
ため。読む側が先に固まっていれば、取り込みのテストで「送られてくる形」を
実物で作れる。

## 11. 同期プロトコル

### 11.1 話しかけるのは常にスマホ側

対等な2台に見えるが、**サーバは PC だけ**。

|          | PC                      | スマホ                          |
| -------- | ----------------------- | ------------------------------- |
| 置き場所 | 自宅 LAN に据え置き     | 持ち歩く                        |
| アドレス | 固定的                  | Wi-Fi に乗るたび変わりうる      |
| 役割     | 受ける（`/api/sync/*`） | 話しかける（HTTP クライアント） |

外出中はスマホに到達できないので、「戻ってきた側が話しかける」が唯一
成立する向きになる。したがって PC 側に足す入口は**受け身の3つだけ**で、
`conventions §1` の両経路対称（REST と Tauri の対）は適用されない ——
PC は受けるだけ、スマホは呼ぶだけで、同じ操作が両経路にある形にならない。

| 入口                       | 向き        | 段  |
| -------------------------- | ----------- | --- |
| `POST /api/sync/handshake` | 確認        | 3a  |
| `POST /api/sync/pull`      | PC → スマホ | 3a  |
| `POST /api/sync/push`      | スマホ → PC | 3b  |

### 11.2 handshake —— 触る前に番号を確かめる

**両端末が同じデバイス番号を名乗ったら、行を1つも動かさずに断る。**

番号が同じということは id の採番レンジが分かれていない（3 節）ということで、
そのまま同期すると別々の行が同じ id を持ったまま混ざる。混ざってから
気付いても、どちらが正かを機械的に判定する手段が無い。設定の書き損じは
起こりうるので、**最初の一言で検出する**。

応答は、相手の番号のほかに次の3つを返す。

- `outboxHead` …… PC 側の変更がどこまで進んでいるか
- `receivedThroughSeq` …… PC が相手から取り込み終えた最後の `seq`（3b で刻む）
- `tables` …… 同期対象のテーブル名（依存順）。相手が知らない表が増えていたら
  気付ける

### 11.3 pull —— 「変更履歴」ではなく「今の姿」を送る

outbox は `(テーブル, 主キー, 操作)` しか持たず、変更前後の値を持たない
（4 節）。pull はこれを**変わった行の目次**として使い、値は現物の表から
読み直す。

- 同じ行が3回変わっていても、送るのは**最後の姿1件**
- ページ境界の後にさらに変わった行は、次のページでもう一度送られる。
  **同じ行を二度送るのは無害**（受け側は同値なら何もしない、6.2）で、
  取りこぼしよりずっと安い
- **墓石も送る。** 削除を伝えないと、相手側に残った行が次の同期で
  こちらへ復活してくる

行は**依存順**（`work_categories` → … → `customers` → `projects` → `trips` →
`work_logs` / `expenses`）に並ぶので、受け側はこの順に流し込めば外部キーで
弾かれない。

### 11.4 進捗の持ち主は「受け取る側」

`afterSeq` は**要求する側が持つ**。サーバが `sync_state` に「ここまで送った」
と記録した値を正にしない。

実際に行を適用したのは要求した側で、応答が途中で切れたことを知っているのも
要求した側だけ。サーバ側で進めてしまうと、**届かなかった変更が二度と
送られない**。多く送り直すのは同値判定で吸収できるが、送られなかったものは
取り返せない。

このため pull は PC の DB を一切書き換えない。`sync_state` を書くのは 3b の
push だけになる。

### 11.5 行の表し方 —— 列の目録を1箇所に持つ

ドメイン型（`Customer` / `WorkLog` …）をそのまま同期に使わない。表示のための
結合列を持ち、`deleted_at` を持たず、8テーブルぶんの直列化と UPSERT を
書くと列を1本足したときに直す場所が増えるため。

代わりに**列の目録**（`sync::rows::SYNCED_TABLES`）を1箇所に持ち、SQL を
そこから組み立てる。目録が実スキーマとずれていないことは、DB 自身に列を
問い合わせるテストが SQLite / PostgreSQL の両方で検査する。0024 で outbox の
記録をトリガに寄せたのと同じ考え方で、「足したのに書き忘れた」を CI で
落とす。

列の型は **TEXT と INTEGER の2種で足りる**。金額は必ず INTEGER（円、
`CLAUDE.md` 1.1）、日付は業務日付の TEXT、真偽値は 0/1、BLOB は無い
（領収書は `attachments` で DB とは別チャネル）。PostgreSQL 側は整数列が
すべて `BIGINT` なので `i64` 一本で両方言を読める。

行はこの形で運ぶ。

```json
{
	"table": "work_logs",
	"key": "1000000042",
	"values": { "id": 1000000042, "minutes": 90, "note": null, "deleted_at": null }
}
```

`values` の列名だけ**スネークケース**（DB の綴りそのもの）なのは意図的。
camelCase へ寄せると列名の変換表が要り、列を足したときに片側だけ直る形の
事故が起きる。`deleted_at` のような同期の要が黙って落ちても気付けない。

### 11.6 push —— 取り込み

1行ごとに、こちらの状態と突き合わせて決める。

| こちらの状態             | 送られてきた版 | 結果                                           |
| ------------------------ | -------------- | ---------------------------------------------- |
| 無い                     | —              | **INSERT**                                     |
| 有る                     | 全列が同値     | **何もしない**                                 |
| 有る・請求済み           | 差がある       | 衝突 `INVOICED_FROZEN`（`force` でも破れない） |
| 有る・こちらも直している | 差がある       | 衝突 `BOTH_CHANGED`（`force` で上書きできる）  |
| 有る・こちらは無変更     | 差がある       | **UPDATE**                                     |

#### 「全列が同値なら書かない」は収束条件そのもの

単なる最適化ではない。取り込んだ行はトリガで outbox に載り（4.1）、次の同期で
送り主へ返る。そこで書き込んでしまうと、両端末が永久に同じ行を送り合う。

同じ理由で、**値は送り主のものをそのまま書く**。`updated_at` をこちらの時計で
上書きすると行が永久に一致せず、同じ無限往復になる。日時は行そのものの属性で、
どの端末で見ても同じであるべき、という意味でも正しい。

id も送り主の値のまま入れる。相手のレンジ（3.1）から出た値なので、こちらの
採番と衝突しない。PostgreSQL の `GENERATED BY DEFAULT AS IDENTITY` が
`ALWAYS` でないのはこのため。

（取り込みぶんが outbox に積まれること自体は抑止しない。1往復だけ余分に
流れるが、同値判定で確実に止まる。抑止の仕組みを入れると「積むべきものを
積み損ねる」方向に壊れる余地ができ、それは取りこぼしとして現れる。
3台目が増えたときに変更が中継されるのも、この積み直しのおかげ。）

#### 「両方で直した」の判定

`pulledThroughSeq` ——「相手が取り込み終えた、**こちらの** outbox の最後の
`seq`」—— を基準線にする。この seq より後にこちらでも同じ行が変わっていれば、
相手はこちらの版を見ないまま直したということで、衝突。

基準線より前なら、相手はこちらの版を見たうえで直している。後から出た意図の
ある変更なので、そのまま取り込む。

#### 足りない列を既定値で埋めない

送り手の不具合で列が落ちたときに「0 円」や `NULL` が正しい値として書き込まれ、
しかも同期は成功したように見える。金額列でこれは踏みたくないので、
目録（11.5）に無い列・足りない列・型の違う列はすべてその場で断る。

#### 並べ替え

依存順（`SYNCED_TABLES` の並び）に直してから流す。pull はこの順で返すので
通常は既に整っているが、順序を送り手の善意に頼ると、外部キー違反という
分かりにくい形で失敗する。

### 11.7 衝突は PC で抱え込まない

**採用（2026-08-21 決定）：衝突した行は取り込まず、応答へ返すだけ。PC は保留
状態を持たない。選ぶのは操作している側。**

- 操作の主体はスマホ（前提）。選ぶ人の手元に置くのが素直
- PC 側にも未解決の山を作ると、同じものを二重に管理することになる。
  「PC で解決したのにスマホにまだ残っている」を防ぐ仕組みが別途要る
- PC は判定と差し戻しに徹すると**状態を持たない**ので、同期が途中で切れても
  PC 側に半端な残骸ができない

利用者が「こちらを採る」と選んだら、その行を `force` 付きでもう一度送る。
「相手のを採る」なら、受け取っている相手の版を自分側に書き込むだけで、
次の同期は同値判定で静かに終わる。

#### 進捗は衝突があっても進める

衝突した行のぶんだけ進捗を止めると、**未解決の1行がその後ろの全部を
堰き止める**。衝突は応答で返しているので失われない。

**その代わり、応答の衝突を保存してから進捗を進めるのは送り主の責任**になる。
保存する前に落ちると、その衝突は次にその行が変わるまで表に出てこない。

#### 請求済みの凍結は `force` でも破れない

`invoiced = 1` の行は両端末とも編集できない（決定 C-20 / 6.1）。請求書は既に
取引先へ渡っている可能性があり、その裏付けを同期の一存で書き換えない。
取消（赤伝）→ 直す → 再発行という F-I8 の手順へ進んでもらう。
