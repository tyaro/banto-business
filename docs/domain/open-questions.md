## A. 税務前提（`tax-calculation.md` 第1章）

### A-1 事業者区分 — **P0**

適格請求書発行事業者 / 免税事業者。

免税事業者の場合、請求書に登録番号欄と税額欄を出せない（出してはいけない）ため、**請求書PDFの様式と Invoice のスキーマが変わる**。

- **決定（2026-08-20）：適格請求書発行事業者。** 登録番号を保持し、請求書に登録番号・税率ごとの対価額・税額・適用税率を記載する。`docs/tax-calculation.md` の記載要件を全て実装する

### A-2 登録番号の保持先 — **P0**

登録番号（`T`+13桁）・氏名／屋号・住所は**設定データ（DB の settings）として保持**し、リポジトリには実値を置かない（`CLAUDE.md` 第8章）。この方針でよいか。

- **決定（2026-08-20）：** settings に保持し、Invoice 確定時に Invoice へスナップショットする。リポジトリには実値を置かない（`CLAUDE.md` 第8章）

### A-3 経理方式と採算の金額基準 — **P0**

税抜経理 / 税込経理。あわせて、**案件採算（売上・原価・粗利）を税抜と税込のどちらで集計するか**を決める。

課税事業者なら消費税は預り金であり、採算は税抜で見るのが実態に合う。免税事業者なら税込が実収入になる。**この選択が採算計算の全ての金額の意味を決める。**

- **決定（2026-08-20）：税抜。** 案件採算の売上・原価・粗利は全て税抜金額で集計する。消費税は預り金として採算に含めない。これにより C-5（1請求書に複数案件がある場合の税額按分）は不要になる

### A-4 課税方式 — **P1**

原則課税 / 簡易課税。申告そのものは範囲外（会計ソフト）だが、簡易課税の場合「預かった消費税の一部が手元に残る」ため、A-3 の採算基準に影響しうる。採算計算では考慮しない（＝税抜のまま）でよいか。A-3 で税抜と決めたため、簡易課税でも採算計算は変わらない。**残る論点は「簡易課税を選んでいる場合に、みなし仕入率による益税を採算に反映するか」のみ**（既定案：反映しない）。

- **決定（2026-08-20）：** 採算計算に反映しない。簡易課税を選んでいても採算は税抜のまま（益税は採算指標に混ぜない）

### A-5 請求書の表示方式 — **P1**

税抜表示（明細は税抜、税額を別掲）/ 税込表示。適格請求書はどちらでも可だが、様式と `TaxLine.amount` の意味が変わる。

- **決定（2026-08-20）：税抜表示。** 明細は税抜金額で並べ、税率ごとの小計と消費税額を別掲する。アプリ内の金額基準（A-3：税抜）と一致するため、表示時の換算・再丸めが発生しない。（既定案：税抜表示。`tax-calculation.md` 第5章の I/F は税抜前提で書かれている）

## B. 税計算の細目（`tax-calculation.md` 第4・7章）

### B-1 端数処理方向 — **P0**

切捨て / 四捨五入 / 切上げ。1円未満。設定値として保持し、Invoice 確定時にスナップショット（既に規約化済み）。

- **決定（2026-08-20）：切捨て（1円未満）。** 設定値として保持し、Invoice 確定時にスナップショットする。設定で四捨五入・切上げも選べるようにする（既発行分は不変）（一般的には切捨てが多い）

### B-2 明細行の `数量 × 単価` の端数 — **P1**

単価を整数円のみに制限して端数を発生させないか、小数単価を許すか。許す場合、行金額の丸めが「税率ごとに1回」の原則と衝突しないよう、行金額の確定方法を決める必要がある。

- **決定（2026-08-20）：** 単価は整数円のみ許容する。工数請求は「時間単価 × 時間」を**行金額として整数で確定**させ、単価側に端数を持ち込まない（行金額の算出方法は `CLAUDE.md` 1.1 に従い切捨てで確定）

### B-3 値引き行（マイナス金額）の許容 — **P0**

許容するか。許容する場合、**税率区分ごとの合計がマイナスになったときの端数処理の定義**（ゼロ方向への切捨て＝絶対値切捨て / 負の無限大方向への切捨て）を明示する必要がある。`CLAUDE.md` 1.1 が「方向と桁を明示」と要求している箇所。

- **決定（2026-08-20）：許容する。端数処理はゼロ方向（絶対値を切捨て）。**

  - 税率区分ごとの合計がマイナスになった場合、`-3,333.5` → **`-3,333`**（ゼロ方向）とする。負の無限大方向（`-3,334`）ではない
  - 実装は「絶対値で切捨ててから符号を戻す」ものとし、テスト T-11 で両方向の差が出るケースを固定する
  - Rust の整数除算はゼロ方向に丸まるため、`i64` の素直な除算がこの定義と一致する（浮動小数点を経由しない）

### B-4 宿泊税・入湯税の分離 — **P2**

宿泊費に含まれる宿泊税・入湯税は不課税。Expense 1件を税区分ごとに分割入力させるか、宿泊費全体を 10% として扱うか（実務上の重要度は低いが、仕入税額控除の正確性に関わる）。

- **決定（2026-08-20）：** 分離しない。宿泊費全体を `STANDARD_10` として扱う。必要な場合のみ明細行を分けて手入力する

### B-5 立替経費を請求するときの税区分 — **P0**

顧客請求対象の経費（交通費・宿泊費等）を請求する際、

1. Expense の税区分をそのまま InvoiceLine に引き継ぐ
2. 立替の実費請求も役務の対価として一律 10%（原則的な扱い）
3. 立替金として課税対象外で請求する

のいずれか。**税額が変わるため推測不可。**

- **決定（2026-08-20）：一律 10%（役務の対価に含めて請求）。** 自分が一度支払い、顧客へ再請求する形とする。InvoiceLine の税区分の既定は `STANDARD_10`。

  - 元の Expense 側の税区分（国際線の不課税など）は**仕入側の記録として保持**し、請求側には引き継がない
  - 行ごとに税区分を変更できる余地は残す（軽減税率の立替が発生した場合に備える）

### B-6 源泉徴収 — **P0**

源泉徴収が発生する契約があるか。ある場合、

- 請求書に「源泉徴収税額」欄と差引後の請求額を記載するか
- 消込時に `WITHHOLDING` として処理するだけにするか

を決める。前者なら Invoice にフィールドが増える。

- **決定（2026-08-20）：発生しない。請求書に源泉徴収欄を作らない。**

  先方が源泉徴収して差し引いて振り込んできた場合は、消込時に `PaymentAllocation` の差額理由コード `WITHHOLDING` で吸収する（`AGENTS.md` 3.7 のコードはそのまま残す）。Invoice 側にはフィールドを追加しない。

### B-7 軽減税率（8%）の発生有無 — **P2**

飲食料品の立替が実際に発生するか。発生しなくても実装とテストは残す（`tax-calculation.md` のケース表を網羅する規約のため）。

- **決定（2026-08-20）：** 現状は発生しない前提。ただし実装とテストケース（T-04 / T-05 / T-07）は残す

### B-8 `EXEMPT`（非課税）と `OUT_OF_SCOPE`（不課税）の使い分け — **P1**

コード値の定義を文書化する（例：印紙・行政手数料＝非課税、海外出張の国際線・保険金＝不課税など）。経費入力時に選び間違えると仕入税額控除の集計が狂う。

- **決定（2026-08-20）：** 用語集に以下を明記する。

  | 区分                     | 該当例                                               |
  | ------------------------ | ---------------------------------------------------- |
  | `EXEMPT`（非課税）       | 印紙税・行政手数料・保険料・住宅家賃                 |
  | `OUT_OF_SCOPE`（不課税） | 国際線運賃・海外での支出・慶弔費・給与・保険金の受取 |

  どちらも消費税額は 0 だが、仕入税額控除の集計上は区別する必要があるため、コード値を分けたまま保持する

## C. ドメイン設計の未決（`plan.md` / `AGENTS.md`）

### C-1 WorkLog の時間の持ち方 — **P0**

`内部原価 = 時間 × 適用単価` を整数円で確定させるため、時間の保持形式を決める必要がある。

1. **分単位の整数**（例：90分）— 端数が出ないが、原価計算で `分 × 単価 ÷ 60` の丸めが必要
2. 0.25時間刻みの整数（15分単位を 1/4 時間として整数管理）
3. 小数時間 — `CLAUDE.md` 1.1 の「浮動小数点禁止」に抵触するため不可

いずれでも**丸めの方向と桁の明示が必要**。

- **決定（2026-08-20）：分単位の整数（`minutes INTEGER NOT NULL`）。** 入力は分単位で自由（90分・45分など）。

  内部原価の計算式と丸め方向を以下に確定する（`CLAUDE.md` 1.1 の「方向と桁を明示」要件）：

  ```
  内部原価（円） = floor(作業分 × 適用時間単価 ÷ 60)
  ```

  - 丸めは**1円未満を切捨て**、`WorkLog` 1行ごとに1回行う
  - 整数演算で行う（`minutes * applied_rate / 60` の整数除算。浮動小数点を経由しない）
  - 案件原価は「丸め済みの行原価の合計」とする（合計してから丸めない）。行ごとに原価が確定していないと明細と合計が一致せず、採算画面で説明できないため（既定案：分単位の整数で保持し、原価は `分 × 時間単価 ÷ 60` を切捨てで円に丸める）

### C-2 内部原価レートの粒度 — **P0**

レートマスタの構造。

1. 単一の時間単価のみ
2. 作業分類別（設計 / 開発 / 移動 …で単価を変える。特に「移動」を安く見積もる運用がありうる）
3. 案件別に上書き可能

`applied_rate` を行に焼き付ける規約（`CLAUDE.md` 1.2）は共通だが、**マスタの形が変わる。**

- **決定（2026-08-20）：作業分類別。** レートマスタは「作業分類 → 時間単価」の1層とする。案件別の上書きは持たない（必要になったら Phase 7 の実運用評価を経て追加を検討）。

  - 「移動」を他より低い単価に設定する運用を想定（実質時間単価の2種併記と整合）
  - 入力時に作業分類の既定単価を `applied_rate` として行へ焼き付ける（`CLAUDE.md` 1.2）。行ごとに手動上書きも可能とする

### C-3 案件売上の定義 — **P0**

案件採算の「売上」を何とするか。

1. 確定済み Invoice の InvoiceLine 合計（＝実際に請求した額。未請求作業は売上に立たない）
2. 契約額（受注時点で確定。請求進捗と無関係）
3. 両方を別指標として表示（契約額 / 請求額 / 入金額）

`plan.md` 第11章の表示候補には契約額・請求額・入金額が並んでいる一方、粗利計算式の「案件売上」がどれを指すか未定義。

- **決定（2026-08-20）：確定済 Invoice の InvoiceLine 合計（税抜）。** 未請求の作業・経費は売上に立たない。契約額は別指標として併記し、粗利計算には使わない。

  帰結：進行中の案件は「原価だけ計上され売上ゼロ」の期間があり、粗利がマイナスに見える。案件詳細画面では**請求進捗（契約額に対する請求済割合）を併記**して誤読を防ぐ。（既定案：粗利は請求額ベース、契約額は進捗比較用に併記）

### C-4 顧客請求対象の経費の二重計上 — **P0**

`billable = true` の経費（顧客に請求する交通費など）は、

- 原価にも計上し、かつ請求額（売上）にも計上する（粗利はゼロ影響）
- 原価から除外する（立替として採算計算の外に置く）

のどちらか。**粗利率と実質時間単価が大きく変わる。**

- **決定（2026-08-20）：両建て。** `billable = true` の経費も原価に計上し、請求した分は売上にも計上する。実費請求なら粗利影響ゼロ、マージンを乗せた分が粗利になる（既定案：両建て。実費請求なら粗利影響ゼロ、マージンを乗せた分だけ粗利になる）

### C-5 1請求書に複数案件がある場合の税額の案件按分 — **P1**

Invoice の税額は請求書単位で確定する（税率ごとに1回の端数処理）。一方、案件採算は案件単位。採算を税抜で見る（A-3）なら按分不要だが、税込で見るなら**按分ルールが必要**。

- **決定（2026-08-20）：按分しない。** A-3 で採算基準を税抜と決めたため、案件採算に消費税は入らない。Invoice の税額は請求書単位でのみ保持する（A-3 に従属）

### C-6 Trip 削除時の挙動 — **P1**

生成された WorkLog / Expense をどうするか。

1. 残して `trip_id` を NULL 化（`AGENTS.md` 3.3 の既定案）
2. 一括削除
3. 確認ダイアログで選択

- **決定（2026-08-20）：** 生成物（WorkLog / Expense）は**残して `trip_id` を NULL 化**する。工数・経費の実績が消えると案件採算が壊れるため、Trip の削除は「出張というまとまりの解除」に留める。削除時は影響件数を表示して確認する

### C-7 Trip 一括生成の既定値 — **P1**

生成ウィザードの入力項目と既定値が未定義。

- 移動 WorkLog の1回あたり時間（往復2件それぞれ）
- 現地作業 WorkLog の1日あたり時間
- 交通費の入力方法（往復合計 / 片道 × 2）
- 宿泊費の入力方法（1泊単価 × 泊数 / 合計額）
- 生成物の作業分類・税区分の既定

- **決定（2026-08-20）：** ウィザードの入力と生成規則を以下とする。

  | 入力                                        | 生成物                                                            |
  | ------------------------------------------- | ----------------------------------------------------------------- |
  | 片道の移動時間（分）                        | WorkLog（作業分類「移動」）を**往復2件**                          |
  | 現地作業の1日あたり時間（分）・現地作業日数 | WorkLog（作業分類「現地作業」）を日数分                           |
  | 交通費（往復合計・円）                      | Expense（分類「交通費」・`STANDARD_10`）1件                       |
  | 1泊単価（円）・泊数                         | Expense（分類「宿泊費」・`STANDARD_10`）1件（金額 = 単価 × 泊数） |
  - 生成物は通常の WorkLog / Expense であり、生成後に個別編集・削除できる
  - `billable` の既定は交通費・宿泊費とも顧客請求対象（true）。案件により変更可

### C-8 支払期限の導出ルール — **P0**

Customer の「締日」「支払条件」から Invoice の支払期限を計算する規則。Overdue 判定（`CLAUDE.md` 1.5）の入力になるため定義が必須。

- 締日の表現（月末 / 20日 / 都度）
- 支払条件の表現（翌月末 / 翌々月10日 / 検収後30日 …）
- 期日が土日祝の場合の扱い（翌営業日 / 前営業日 / 調整しない）
- 祝日マスタを持つか（持たないなら「調整しない」しか選べない）

- **決定（2026-08-20）：顧客マスタに「締日」と「支払条件」を保持し、Invoice 作成時に支払期限を自動計算する（手修正可）。土日祝の調整は行わない。**

  保持形式（`CLAUDE.md` 1.1 の趣旨に沿い、曖昧な文字列ではなくコード値で持つ）：

  | 項目                   | 表現                                                   |
  | ---------------------- | ------------------------------------------------------ |
  | `closing_day`          | 1〜28 の日、または `99`（月末）                        |
  | `payment_month_offset` | 締日から何ヶ月後に支払われるか（1 = 翌月、2 = 翌々月） |
  | `payment_day`          | 1〜28 の日、または `99`（月末）                        |

  例：「月末締め・翌月末払い」＝ `closing_day=99, payment_month_offset=1, payment_day=99`

  - 支払期限は Invoice に**確定値として保存**する（Customer のマスタ変更が過去の Invoice に波及しないこと。`CLAUDE.md` 1.2 と同じ考え方）
  - 土日祝で期日がずれる運用は**アプリでは調整しない**（祝日マスタを持たないため、推測で前後させると実態とずれる）。必要なら Invoice 作成時に手修正する
  - Overdue 判定（`CLAUDE.md` 1.5）はこの保存済み支払期限を使う

### C-10 Invoice 取消（赤伝）の関連付け — **P1**

`Cancelled` にした請求書と、その差し替えで発行する新しい請求書を関連付けるか（`corrected_invoice_id` 等）。適格請求書の訂正では「修正した適格請求書の交付」が必要で、元請求書との対応を残すのが実務上安全。

- **決定（2026-08-20）：** Invoice に `corrected_invoice_id`（取消した元請求書への参照）を持つ。適格請求書の訂正では「修正した適格請求書の交付」が必要であり、元請求書との対応を残す

### C-11 過入金（`OVERPAYMENT`）の扱い — **P1**

充当額が請求額を超える入金を許容するか。許容する場合、超過分を前受金として次回請求に充てる仕組みまで作るか、備考で運用するか。

- **決定（2026-08-20）：** 充当額が請求額を超える入金を許容し、超過分は `OVERPAYMENT` 理由コードで記録するのみとする。残額はマイナスにしない（0 で止める）。前受金として次回請求へ繰り越す仕組みは作らない

### C-12 Project の状態定義 — **P1**

`plan.md` 7.3 に「状態」とあるだけで値が未定義。例：`見込 / 受注 / 進行中 / 検収待ち / 完了 / 失注 / 保留`。採算集計の対象にどの状態を含めるかも決める。

- **決定（2026-08-20）：** `見込 / 受注 / 進行中 / 検収待ち / 完了 / 失注 / 保留` の7状態。

  - 案件採算の集計対象は**失注を除く全状態**
  - ダッシュボードの「進行中案件」は `受注 / 進行中 / 検収待ち` を指す

### C-13 通貨 — **P2**

日本円のみでよいか（外貨建て請求の予定はあるか）。

- **決定（2026-08-20）：** 日本円のみ。通貨コードのカラムを持たない（多通貨は非対応）

### C-14 単価の時期変動 — **P2**

残業・休日・深夜で内部原価レートを変えるか。変えないなら C-2 の粒度で足りる。

- **決定（2026-08-20）：** 残業・休日・深夜での単価変動は持たない。C-2 の作業分類別レートで足りる

## D. 運用・環境

### D-1 利用者 — **P2**

単一利用者（本人のみ）か。Banto の RBAC / ログイン画面をそのまま使うか、実質単一ユーザー運用にするか。

- **決定（2026-08-20）：** 実質単一利用者。ただし Banto の認証・RBAC はテンプレート標準のまま残す（無効化する改変を入れない。`CLAUDE.md` 第2章）

### D-2 領収書の添付範囲 — **P2**

Attachments に置くのは案件紐付けが必要なものだけか（正本は会計ソフト側、`CLAUDE.md` 1.6）。

- **決定（2026-08-20）：** 案件紐付けが必要なもの（Expense の領収書）のみ Attachments に置く。正本は会計ソフト側（`CLAUDE.md` 1.6）

### D-3 日付の扱い — 確認のみ

業務日付は JST のローカル日付を `TEXT`（ISO 8601）で保持（`CLAUDE.md` 第4章で決定済み）。時刻は持たない。この前提で進めてよいか。

- **決定（2026-08-20）：** 業務日付は JST のローカル日付を `TEXT`（ISO 8601 `YYYY-MM-DD`）で保持し、時刻は持たない。監査ログ等の技術的なタイムスタンプは Banto の既定に従う
