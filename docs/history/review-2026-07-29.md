## 0. 結論

設計と検証機構の質は、この種のテンプレートとしてはかなり上位。ただし
「今日クローンして出荷できるか」という意味では**出荷ブロッカーが1件**ある。

その1件は i18n のビルドが CDN 依存で、**失敗してもビルドが成功扱いになり、
文言が全部消えた成果物を吐く**こと（§2）。しかも最終的に画面が真っ白になる
種類の壊れ方をする。CI はネットワークがあるので緑のままで、この経路は上流で
一度も検出されない。

逆に言えば、そこを直せば「使い物になる」側の評価。

着手順の推奨:

1. §2（出荷ブロッカー）
2. §3（「二形態」という売り文句の裏付け）
3. §4（投資済み資産の回収）

§2 と §4 は半日仕事の規模。

## 2. [Blocker] i18n ビルドが CDN 依存かつ fail-open

### 現象

`apps/admin-template/project.inlang/settings.json` がコンパイル時プラグインを
jsdelivr の URL で参照している。取得に失敗すると WARN を出した直後に
「Successfully compiled」と表示して **exit 0** を返し、空のメッセージカタログを
出力する。

### 根拠（実測）

- 該当箇所: `settings.json` の `modules`
  - `https://cdn.jsdelivr.net/npm/@inlang/plugin-message-format@4.4.0/dist/index.js`
  - `https://cdn.jsdelivr.net/npm/@inlang/plugin-m-function-matcher@2.2.6/dist/index.js`
- `grep -c "plugin-message-format" pnpm-lock.yaml` → **0**
  （lockfile に不在＝ `pnpm install --frozen-lockfile` の再現性保証の外側）
- `node_modules` にも存在しない（毎ビルド CDN 取得）
- 閉域環境での `pnpm paraglide:compile` 出力:
  - `WARN [paraglide-js] PluginImportError: Couldn't import the plugin ...`
  - `√ [paraglide-js] Successfully compiled inlang project.` / `EXIT=0`
  - `src/lib/paraglide/messages/_index.js` が実質2行（メッセージ0件）
- `pnpm check` → **420 errors**
- `pnpm build` → **exit 0**、`IMPORT_IS_UNDEFINED` 警告 **1380件**
- 生成物 `apps/admin-template/build/` を grep しても
  「ダッシュボード / 商品 / ログイン」が0ヒット

### 影響

参照側が `src/lib/navigation.ts:44` の `m[item.labelKey]()` のような**動的キー
呼び出し**のため、`m[key]` が `undefined` → `undefined()` の **TypeError** になる。
文言が空欄になるのではなく画面が落ちる。

CI はネットワークがあるため常に緑で、この経路は上流で一度も検出されない。
被害が出るのは社内プロキシ・閉域網など、README が掲げるターゲット
（現場端末 / LAN 運用の業務系）そのもの。

### 方針との不整合

CI は「タグは可変＝サプライチェーンリスク」として GitHub Actions を全て
コミット SHA でピン留めしている（`ci.yml` 冒頭コメント）一方、**ビルド時に
実行されるコードを整合性検証なしで CDN から取得**している。
conventions §3「依存を足さない」とも方向が逆。

なお [ADR-0005](../adr/0005-i18n-paraglide.md) は Paraglide を「コンパイル時 i18n で
**実行時依存**が極小」という基準で採用しており、その判断自体は妥当。本件が突いて
いるのは実行時依存ではなく**ビルド時依存の入手経路**であり、ADR-0005 の結論を
覆すものではない。

### 対応案

1. `@inlang/plugin-message-format@4.4.0` /
   `@inlang/plugin-m-function-matcher@2.2.6` を devDependency として追加し、
   `settings.json` をローカル参照に切り替える
   （npm 上に同一バージョンが存在することは `npm view` で確認済み）
2. `paraglide:compile` の後段に **メッセージ件数0なら異常終了**するガードを
   追加する。fail-open が被害の大半を占めており、1 だけでは CDN 以外の失敗
   要因に対して無防備なため、**2 は 1 とセットで必須**
3. 可能なら CI に「ネットワーク遮断でのビルド」ジョブを1本追加して回帰を防ぐ

## 3. [High] Tauri 側 48 コマンドのテストがどの CI ジョブでも実行されていない

### 現象

「デスクトップ + LAN の二形態」が売りだが、デスクトップ半分の検証が最も薄い。

### 根拠（実測）

- `apps/admin-template/src-tauri/src/lib.rs` = **2645行 / `#[tauri::command]` 48個**
  （README は「薄いコマンドアダプタ」と表現しているが、もう薄くない）
- 同ファイル内の `#[test]` / `#[tokio::test]` は **8個**
- メイン CI（`.github/workflows/ci.yml`）の rust ジョブは `admin-template` を**除外**
- `.github/workflows/tauri-check.yml` は
  `cargo check -p admin-template --all-targets` のみ → コンパイルは通すが**実行しない**
- 結果、この8個のテストは**どこでも走っていない**

### 影響

最重要不変条件 §1「両経路対称」がかかっている場所。conventions §1 自身が
「機械検査が見るのは**両経路に存在するか**まで。**認可レベルと監査記録が実際に
同一か**はコード + テストで担保する（rule 8 の対象外）」と明記している。

つまり 48 コマンドの認可・監査の正しさは「存在マニフェスト + 人間のコード
レビュー」だけで担保され、実行されるテストは 0。

加えて AGENTS.md が「サンドボックスでは `src-tauri` はコンパイル不可」と宣言して
いるため、AI エージェントに委譲した場合は型検査すら通せない。これは
maintainability-review §1-3 が指摘した「起動しないと検証できない領域は AI の
盲点」そのものが、最も重要な不変条件の上で現実化している状態。

### 対応案

`tauri-check.yml` の `cargo check -p admin-template --all-targets` に加えて
`cargo test -p admin-template` を実行する。`--all-targets` が既に通っている
以上、追加コストはテスト実行時間のみ。

## 4. [Medium] `scaffold.mjs` が導線のどこにも露出していない

### 現象

テンプレート利用者にとって最も価値の高い自動化が、利用者から見つけられない。

### 根拠（実測）

- `scripts/scaffold.mjs` = **930行**、`scripts/scaffold.test.mjs` = 62行
- 機能: `--preset minimal|standard|full` / `--interactive` / `--dry-run`
  （README「3. オプション資産の削除」を 1 対 1 で自動化）
- 露出状況:
  - `package.json` の scripts に **無い**
  - `README.md` / `README.en.md` に **無い**
  - `AGENTS.md` / `docs/recipes/add-resource.md` に **無い**
  - 言及は `CHANGELOG.md` / `scaffold-presets-plan.md` /
    `improvement-plan-2026-07.md` のみ

### 影響

テンプレートをコピーした人は README §3 の手作業に従うことになる。添付機能の
削除は6ステップあり、途中に「外さないと `cargo test` がコンパイルできない」と
いう注意書きまである。**動く自動化があるのに、手順書を読みながら手でやらせて
いる。**

実装の問題ではなく完全に導線の問題であり、修正コストは極小。

### 対応案

- `package.json` に `"scaffold": "node scripts/scaffold.mjs"` を追加
- README §3 の冒頭に「まず `pnpm scaffold --preset <preset>` を試す。手動手順は
  以下（scaffold が触らない資産・独自に削りたい場合）」を1節追加
- AGENTS.md「タスク別の入り口」にも1行

## 5. [Low] その他

### 5.1 e2e の `afterAll` が無防備な `page.close()` で真因を隠す

`e2e/tests/smoke.spec.ts:107-109` が `await page.close()` を無防備に呼んでいる。
`beforeAll` が失敗すると `page` が undefined のまま `afterAll` が走り、
`TypeError: Cannot read properties of undefined (reading 'close')` が本当の失敗
原因を覆い隠す。実際にこれを踏み、真因（Playwright ブラウザ未インストール）への
到達に一手余計にかかった。

対応: `await page?.close();` に変更する。

記録のみ（対応不要）:

- スイート全体が `describe.serial` + 共有状態のため 1件失敗で残り12件が未実行に
  なる。モジュール冒頭コメントで意図的な設計と明記されており、スモークとしては
  妥当な割り切り。
- E2E が `'ユーザーメニューを開く'` 等の日本語文字列を直接アサートしており、
  ja ロケール表示に固定的に結合している。

### 5.2 Remember me の「再起動でセッション消失」が README 側に無い

セッショントークンは `crates/banto-server/src/auth.rs:286` の
`tokens: RwLock<HashMap<String, TokenRecord>>` によるインメモリ保持で、プロセス
再起動で全て失われる。

仕様としては [roadmap.md](../roadmap.md) の未決事項一覧に**受容済みの判断として記録
あり**（「LAN側 Remember me → サーバ再起動でセッションが切れる仕様を v1 では
許容」）。ただし利用者が読む README には「絶対8時間 / アイドル1時間」
「Remember me 30日 / 7日」という約束のみが見える。デスクトップアプリが毎日
再起動される前提だと 30日 は名目値になる。

実装の欠陥ではなく**ドキュメントの置き場所**の問題。README「LANアクセス」節の
セッション説明に1文追加すれば足りる。

## 6. 導入コストの現実（所見・対応不要）

README は「新しい CRUD リソースを1本通すには9ステップ必要」と正直に書いている。
手本となる `apps/admin-template/core/src/items.rs` は 1171行（実装674行 +
テスト約500行）あり、差し替え対象としてはかなりの分量。

これは 2026-07-18 に「動的ルート自動導出ではなくコピーして書き換える」と明示的に
決定された結果で、「利用者が読み解けない魔法を増やさない」という理由も
[recipes/add-resource.md](../recipes/add-resource.md) に記録されている。判断としては
筋が通っており、レシピ自体も67行の具体的なチェックリストで AI にそのまま渡せる
品質。

ただしトレードオフは正直に見るべきで、**このテンプレートの生産性は「AI にレシピを
回させる」前提に強く依存する**。人間が手で9ステップ × リソース数をこなす前提なら、
コスト構造は率直に言って良くない。README の「AI 併走で量産したい人」という対象
読者の書き方は、その意味で正確。

## 7. 強い点（実測して確認したもの）

批判と同じ精度で記録する。

**`verify:architecture` が本物。** 10個の不変条件を機械検査し、全て通過している。
サービス層21ファイルの transport 非依存、パッケージ間 import ゼロ、`{@html}` の
許可リスト2箇所、生色値の不在、両経路20対の分類完全性、`NewAttachment` に mime
フィールドが無いこと、`settings_get` / `settings_set` の Admin 対称性まで見ている。
規約をドキュメントに書いて終わりにしているプロジェクトが大半の中で、ここまで実行
可能な形に落としている例は珍しい。さらに「機械検査できるのはここまで、残りは
レビュー」という境界を conventions.md が自分で明示しているのが良い。AI 併走での
保守を成立させているのは実質この機構。

**セキュリティの作り込みが考えて書かれている。** ログインのスロットルが
per-(IP+username) と per-IP の2次元で、その理由が「argon2 は未知ユーザーでも
ダミーハッシュを回すので、username をローテーションされると CPU 枯渇 DoS になる」
と doc コメントに書かれ、`per_ip_dimension_bounds_a_username_rotation_flood` という
攻撃名そのものの回帰テストまである。MIME のマジックバイト判定、ファイルパスに
ユーザー入力を使わない設計、`ColumnMap` ホワイトリスト、セキュリティヘッダを
最外層に置いて「新ルートが opt-in を忘れても漏れない」構造 — いずれも後付けでは
なく最初から意図されている。

**`packages/report/src/core/html.ts`** の "no 'trusted' string anywhere in this
module" は、`{@html}` に食わせる文字列を作る側の正しい書き方。テンプレート由来
テキストとデータ由来テキストを同じエスケープ経路に通し、例外を作っていない。

**README の正直さは資産。** 「向いていない人」を明示し、v1 の割り切りを列挙し、
TLS 未対応を警告ブロックで書いた上で Caddy の設定例を出し、さらに「プロキシ経由
だと per-IP レート制限が全クライアント合算で発火する」という、普通は運用で踏んで
から気づく落とし穴まで先回りして書いてある。

**`rename.mjs` がよく出来ている。** `--dry-run` で13箇所の書き換えを列挙した上で、
「スクリプトがやらないこと」6項目（アイコン、LICENSE、visual スナップショット
再生成、identifier 変更でアプリデータが引き継がれない件まで）を出力する。

**依存の絞り込みは建前ではない。** `@banto/*` 全パッケージの
dependencies / peerDependencies が空であることを実測で確認。チャート14種は SVG
フルスクラッチ。ADR に却下案まで残っている。

## 8. 適合判断

**勧められる** — Tauri + SvelteKit + Rust の構成が決まっていて、デスクトップと
LAN ブラウザの両方が要る業務系で、AI にレシピを回させて量産する運用を取る場合。
認証・RBAC・監査ログ・設定基盤・バックアップまで最初から入っている状態は、ゼロ
から組むと数週間かかる。不変条件の機械検査があるおかげで、AI が壊した場合に CI が
捕まえてくれる範囲も広い。

**勧められない** — Web のみ / デスクトップのみで足りる場合（二形態の複雑さが全部
コストになる）、React エコシステムに乗りたい場合、そして**リソースを大量に追加する
予定で AI 併走を前提にしない場合**（9ステップ × N の手作業になる）。

これは README「対象読者 / 非対象」の記述とほぼ一致しており、テンプレート側の自己
認識は正確。
