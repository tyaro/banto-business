# Banto フィードバックログ

Banto Business の開発中に見つかった Banto 本体への課題を記録する。

**記録開始：Phase 2**（ただし Phase 0/1 でも Banto 由来の摩擦に気づいた時点で記録する。「後でまとめない」原則を優先）

---

## なぜ逐次記録するか

計画書 第22章の第二の成功条件は「Banto が汎用的な業務アプリケーション基盤として成立していることの実証」である。この検証根拠がこのファイルになる。

最も価値のある摩擦は開発初期に発生するが、開発が進むと慣れによって「そういうもの」として受け入れられ、後から思い出せなくなる。**開発完了後にまとめて振り返らない。気づいた時点で記録する。**

---

## 記録ルール

1. **その場で書く。** 後でまとめようとしない
2. 回避策を実装したら必ず記録する（回避策の存在自体が Banto の課題の証拠）
3. 分類が判断できない場合は `未分類` のままでよい。分類より記録が優先
4. Banto 側へ還元するのは `Banto共通` のみ。`Business固有` は還元しない

---

## 分類基準

| 分類 | 判断基準 |
|---|---|
| `Banto共通` | Industrial でも他ドメインでも同様に発生しうる。フレームワークの汎用性の問題 |
| `Business固有` | 事業管理ドメイン特有。Banto に持ち込むと汎用性を損なう |
| `未分類` | 判断保留 |

**迷ったら `未分類` で記録し、Phase 完了時にまとめて判断する。**

### [2026-08-20] Phase 8 — `append_where` に基底の述語を渡せない

| 項目 | 内容 |
|---|---|
| 事象 | `banto_storage::list_query::{sqlite,postgres}::append_where` は `filters` が空でないときだけ ` WHERE ` を出す。そのため一覧の基底 SELECT に**サービス側の固定条件**（今回は論理削除の `deleted_at IS NULL`）を書けない —— 絞り込み付きの一覧が `SELECT ... FROM t WHERE deleted_at IS NULL WHERE code = ?` になって落ちる |
| 影響 | Business 固有ではない。「一覧から常に除きたい行」はテナント分離・アーカイブ・論理削除など、業務アプリで普通に出る要求。`ColumnMap` による列の whitelist という良い設計があるのに、**述語の合成だけが呼び出し側でできない** |
| 回避策 | app 層で派生表に包む: `(SELECT * FROM t WHERE deleted_at IS NULL) AS t`（`crate::sync::live`）。別名を元の表名に揃えると外側の `ORDER BY` / 絞り込みが列名をそのまま使え、PostgreSQL の「派生表には別名が要る」も満たせる。両方言で同じ SQL が通る |
| 分類 | Banto共通 |
| Banto Issue | 未起票 |
| 状態 | 回避済み。`append_where` が基底の述語（または「既に WHERE を出したか」の状態）を受け取れれば派生表は要らない。**代案として `params.filters` へ `deletedAt is_null` を差し込む方式も検討したが採らなかった** —— `deletedAt` を絞り込み可能な列として公開することになり、呼び出し側の書き方次第で墓石が見えてしまう。派生表なら外側にどんな絞り込みが付いても原理的に見えない |
