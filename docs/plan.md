## 1. プロジェクト概要

### 名称

Banto Business

### リポジトリ

`tyaro/banto-business`

### 目的

個人事業における以下の業務を一元管理するデスクトップアプリケーションを開発する。

- 顧客管理
- 案件管理
- 開発工数管理
- 現地工数管理
- 移動工数管理
- 出張管理
- 交通費 / 宿泊費 / 送料 / 部材費 / その他案件経費
- 案件原価
- 案件採算
- 請求書作成
- 入金管理

Excelによる案件・経費・請求管理から脱却し、日常的な入力から請求・案件採算確認までをBanto Business上で完結させる。

## 4. Bantoバージョン管理

Banto BusinessからBantoへの依存は原則としてgitタグで固定する。

```
Banto Business
      ↓
Banto vX.Y.Z
```

開発中にBantoのmainブランチへ無条件追従する構成は避ける。これにより、

- Banto更新による突然の破壊を防止
- Banto Industrialとのバージョン管理を明確化
- Banto側の変更とBusiness側の変更を分離

する。

Bantoの新バージョンへ更新する場合は、Banto Business側で動作確認を行ってから依存タグを更新する。

### 4.1 テンプレート由来コードの追従方針

パッケージ依存はタグ固定で管理できるが、**テンプレートから派生したボイラープレート**（Tauri設定、CI定義、ディレクトリ構成、ビルドスクリプト等）は派生時点で独立し、以後自動追従しない。

放置するとIndustrial / Businessの2つの派生先で構成が徐々に乖離するため、以下を方針とする。

- テンプレート由来ファイルには派生元のBantoタグを記録する（`docs/template-origin.md`）
- Banto側テンプレート更新時は、差分を確認して**手動で選択的に取り込む**
- 取り込み判断（採用 / 見送り / 理由）を同ファイルに追記する
- 全面同期は行わない

## 5. 技術構成

Banto標準構成を基本とする。

### Platform

- Tauri v2
- Rust
- SvelteKit
- Svelte 5
- TypeScript

### Database

初期版：**SQLite**

一人利用・ローカルファーストを基本とする。
将来的な複数端末・複数ユーザー利用が必要になった場合は、BantoのPostgreSQL対応を利用する。

### 金額の取り扱い（全体規約）

- 金額は必ず **INTEGER（円単位）** で保持する。`REAL` / 浮動小数点は使用しない
- 税率・率系の値は分子分母または basis point（1/10000）で保持する
- 端数処理の方向と桁は、税計算・原価計算それぞれで明示的に定義する（第13章参照）

## 6. システム境界

Banto Businessは会計ソフトではない。

### 担当範囲

```
顧客
 ↓
案件
 ↓
作業
 ├─ 工数
 ├─ 出張
 └─ 経費
 ↓
案件原価
 ↓
請求
 ↓
入金
 ↓
案件採算
```

### 対象外

- 複式簿記
- 仕訳帳
- 総勘定元帳
- 決算
- 確定申告
- 法人税申告
- 給与計算

税務・会計処理は既存会計ソフトを使用する。必要になった場合のみCSV/API連携を追加する。

### 6.1 証憑（領収書等）の正本の所在

領収書等の**正本は会計ソフト側**に保持する。

Banto Business の Attachments に保存する領収書画像・PDFは、**案件紐付けと採算確認のための参照コピー**と位置付ける。

理由：正本として扱う場合、電子帳簿保存法上の要件（検索要件、訂正削除履歴の保存等）を満たす必要が生じ、システム境界（会計ソフトではない）と矛盾するため。

この方針を `AGENTS.md` にも明記し、後から「Banto Businessだけで完結させる」方向へ暗黙に拡大しないようにする。

## 8. WorkLog

案件単位で工数を記録する。

### 作業分類例

- 設計
- PLC開発
- SCADA開発
- PCアプリ開発
- テスト
- 社内調整
- 現地作業
- 移動
- 打合せ
- その他

### 記録項目

| 項目 | 備考 |
|---|---|
| 日付 | |
| 案件 | |
| 出張 | Tripに属する場合 |
| 作業分類 | |
| 時間 | |
| 作業内容 | |
| **適用単価** | **記録時点の内部原価レートを行に焼き付ける** |
| 内部原価 | 時間 × 適用単価 |

### 8.1 原価レートのスナップショット

内部原価はレートマスタを**参照**するのではなく、**記録時点の単価を行に保存する**。

理由：後から時給設定を変更したとき、過去案件の採算が遡って書き換わると、第11章の指標および過去の意思決定の妥当性が検証できなくなるため。

レートマスタは「新規入力時のデフォルト値の供給源」としてのみ機能させる。

案件ごとの総投入時間を算出する。

生成物は通常のWorkLog / Expenseレコードであり、Trip削除時の挙動（残す / 一括削除 / 確認）は Phase 1 で定義する。

## 11. 案件採算

### 基本指標

```
案件売上
 -
工数原価
 -
交通費
 -
宿泊費
 -
部材費
 -
送料
 -
その他直接経費
 =
案件粗利
```

### 実質時間単価

```
案件粗利 ÷ 総投入時間
```

**移動時間の扱いにより数値が大きく変わるため、2通りを併記する。**

| 指標 | 分母 |
|---|---|
| 実質時間単価（移動込み） | 全WorkLog時間 |
| 実質時間単価（移動除く） | 作業分類「移動」を除いたWorkLog時間 |

案件受注可否の判断にはこの差が直接効くため、片方のみの表示は行わない。

### 表示候補

- 契約額
- 請求額
- 入金額
- 総工数 / 移動時間
- 工数原価
- 直接経費
- 粗利
- 粗利率
- 実質時間単価（移動込み / 移動除く）

## 12. Invoice

### 12.1 構造

`Project → Invoice` の 1対1 構造は採用しない。

実務上、以下が両方発生するため。

- **1請求書に複数案件**：同一顧客の複数案件を締日でまとめて1枚にする
- **1案件に複数請求書**：着手金 / 中間金 / 検収後で分割する

したがって以下の構造とする。

```
Invoice (顧客・締日・支払期限を保持)
   └─ InvoiceLine
         ├─ project_id  （どの案件の売上か）
         ├─ 品目
         ├─ 数量 / 単価 / 金額
         └─ 税区分
```

案件採算（第11章）の「請求額」は、その案件を参照する InvoiceLine の合計として算出する。

> Customer に締日・支払条件を持たせている設計とも、この構造が整合する。

### 12.2 請求明細例

- PLCソフト開発
- SCADA開発
- PCソフト開発
- 設計
- 現地調整
- 交通費
- 宿泊費
- 部材
- 送料
- その他

### 12.3 処理フロー

```
Project / 期間 / 顧客
   ↓
請求対象選択（未請求のWorkLog・Expense）
   ↓
Invoice Draft
   ↓
明細確認・編集
   ↓
税計算
   ↓
Invoice確定（明細を確定値としてスナップショット）
   ↓
PDF生成
```

確定後は元データ（WorkLog / Expense）の変更が請求書に波及しないよう、確定時点の値を保持する。

PDF生成については Banto の Report 機能を優先的に利用する。

## 13. 適格請求書（インボイス制度）対応

請求書PDFを実運用で使用するため、適格請求書の記載要件を満たす。**Phase 1 の設計成果物に含める。**

### 必須記載事項

- 適格請求書発行事業者の氏名または名称
- **登録番号（T + 13桁）**
- 取引年月日
- 取引内容（軽減税率対象品目である旨を含む）
- **税率ごとに区分して合計した対価の額（税抜または税込）**
- **税率ごとの消費税額および適用税率**
- 交付を受ける事業者の氏名または名称

### 端数処理規約

- 端数処理は**1つの適格請求書につき、税率ごとに1回**
- 明細行ごとの個別端数処理は行わない
- 端数処理方向（切捨て / 四捨五入 / 切上げ）を設定値として保持し、既定を定める

### データモデルへの影響

- Invoice に登録番号・端数処理方向・税抜/税込区分を保持
- InvoiceLine に税区分（10% / 8%軽減 / 不課税 / 非課税）を保持
- Invoice に税率区分ごとの集計（対象額・消費税額）を確定時にスナップショット

> ここは後付けが最も困難な箇所であり、「税計算」の一言で先送りしない。

## 14. Payment

### 14.1 構造

`Invoice ↔ Payment` を 1対1 としない。

差額の発生要因が複数あるため。

- 一部入金（分割入金）
- 複数請求のまとめ入金
- 振込手数料の先方差引
- 源泉徴収（契約内容により発生しうる）

したがって消込テーブルを介した N:M 構造とする。

```
Invoice ──┐
          ├─ PaymentAllocation ──┐
Payment ──┘   ├─ 充当額           │
              └─ 差額理由コード   │
                                  ↓
                          残額 = 請求額 - 充当額合計
```

### 14.2 差額理由コード

- 振込手数料
- 源泉徴収
- 値引き
- 過入金
- その他（要備考）

### 14.3 状態遷移

```
Draft
 ↓
Issued
 ↓
Partially Paid ⇄ Paid
 ↓
Cancelled（赤伝）
```

変更点：

- `Issued` と `Waiting Payment` は実質同一のため **`Issued` に統合**
- `Partially Paid` を追加
- `Cancelled` を追加
- **`Overdue` は状態として持たない**

### 14.4 Overdue を導出値とする理由

`Overdue` を状態として保持すると、日次で状態を更新するバッチ処理が必要になる。アプリを起動しない日が発生するローカルファースト構成とは相性が悪く、状態が実態とずれる。

したがって以下の**導出条件**として都度評価する。

```
Overdue := (支払期限 < 今日) AND (残額 > 0) AND (状態 ≠ Cancelled)
```

### 14.5 管理項目

- 請求額
- 支払期限
- 入金日
- 入金額
- 充当額 / 残額
- 差額理由

未入金・期限超過をダッシュボードへ表示する。

### Phase 8 ― デバイス間同期（PC ⇄ Android）

> **2026-08-24 運用転換。** 実機実験の結果、双方向同期ではなく**スマホ母艦**
> （スマホの DB を正本にし、PC はブラウザで接続）を正式な運用にした。
> 同期のコードは残る。経緯と判断は `docs/domain/sync.md` 0節。

**スマホを操作の主体にする。** 工数・経費・出張の入力は外出先で行い、PC は
大画面での整理と、請求・入金・採算のためのデスク作業に使う。

```
外出先        Pixel（ローカル SQLite・完全オフライン）
   │
   │ 帰宅して LAN に乗る
   ▼
自宅 LAN      Pixel  ⇄  banto-serve（PC）
```

外出先ではオフライン、同期は自宅 LAN に戻ったときだけ。**インターネットに
何も公開しない**（クラウドも VPN も使わない）。

**方式の詳細は `docs/domain/sync.md`。** 要点のみ：

- 双方向にするのは 8 テーブル（顧客・案件・各マスタ・工数・経費・出張）
- **請求・入金は PC 専用。** 請求書番号がオフライン 2 台で重複しうるため
- id はデバイス別レンジ（PC 1〜 / Pixel 10億〜）。既存データの振り直しは不要
- 変更追跡は outbox テーブル（`updated_at` は秒精度なので使わない）
- 削除は論理削除（トゥームストーン）
- 衝突は自動解決せず提示する
- 新規依存は足さない（`ADR-0002`）

**実装の順序**

1. スキーマ（デバイスレンジ / outbox / 論理削除）
2. サービス層（論理削除への移行・outbox 記録）
3. 同期プロトコル（PC 側）— ここまで Android 無しでテストできる
4. Android ビルド
5. クイック入力（工数1件。当初は「折りたたみ外側専用の画面」の想定だったが、実機で外側も通常の画面が使えると分かったため `docs/domain/sync.md` 8.1 で前提を訂正）

## 19. Bantoへのフィードバック

Banto Business 開発中に見つかった問題を、

- **Business固有問題**
- **Banto共通問題**

に分類する。共通問題のみ Banto 側へ還元する。

```
Banto Business
      │
      │ 共通機能として有用
      ↓
    Banto
      │
      │ 新タグ
      ↓
Banto Business更新
```

Business固有機能を Banto へ逆流させない。

### 19.1 フィードバックの常設ログ化

第22章の第二の成功条件（Bantoの汎用性実証）を検証可能にするため、フィードバックは開発完了後にまとめて振り返るのではなく、**Phase 2 の時点から `docs/banto-feedback.md` に逐次記録する。**

記録内容：

| 項目 |
|---|
| 発生Phase / 日付 |
| 事象（Bantoに足りなかった / 想定と違った点） |
| 回避策 |
| 分類（Business固有 / Banto共通） |
| Banto側Issue番号（該当時） |

理由：最も価値のある摩擦は初期に発生するが、開発が進むと慣れによって忘れられ、後から思い出せない。

AGENTS.md
CLAUDE.md

- 禁止事項
